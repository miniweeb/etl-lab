# Glossary

Every term below is taught properly somewhere in A00–A15; this page is the
place to look it up again when it resurfaces five assignments later.

| Term | Meaning | Taught in |
|---|---|---|
| **schema (table)** | The declared columns and types of a dataset — what you *expect*, as opposed to what arrives. | A01 |
| **staging / core / marts / ops** | Warehouse layers: 1:1 landed source data (source-prefixed) / conformed business entities / consumption tables / pipeline metadata. | A03 |
| **grain** | What one row represents (one order? one order *line*? one store-day?). Every table has exactly one — and a table whose grain you cannot say in one sentence is a table you have not designed. | A03, A04, guides/data_modeling.md |
| **fact table** | A table of events at a stated grain, carrying the measures people sum: `core.orders` (one row = one *delivered version* of an order — corrections re-deliver, so one-row-per-order only arrives once A08 folds them; `fct_orders` in A15 is the deduped one) and `core.order_items` (one row = one line of one delivered version, `qty` and `unit_price`). Facts are *chosen*, not inherited — two grains means two fact tables, which is why unnesting items got its own table instead of more columns on orders. | A03, A15 |
| **dimension table** | A table describing the entities a fact points at — `core.customers`, `core.products`, `core.stores` — holding the attributes you filter and group by (country, category, region). One row per entity; the fact keeps only the id. | A03, A15 |
| **star schema** | Fact in the middle, dimensions one join hop away all around it — what `marts.daily_store_sales` is built from (`fct_orders` ⋈ `dim_stores`). You build one in A03 before you get the word: `core.orders_enriched` is a fact joined to its dimensions. | A15 |
| **snowflake schema** | A star whose dimensions are themselves normalized into sub-dimensions (product → category → department as separate tables): fewer repeated strings, more joins on every query. Named for recognition — this lab keeps its dimensions flat, category and subcategory as plain columns on `dim_products`. | guides/data_modeling.md |
| **transaction / periodic-snapshot / accumulating-snapshot fact** | The three fact shapes: one row per event (`fct_orders`, `fct_order_items`); one row per entity per period (`marts.daily_store_sales` — one per store, day and currency); one row per process instance with a column per milestone (an order-lifecycle table with paid/shipped/delivered timestamps, updated in place — named here, not built). | A15 |
| **additive / semi-additive / non-additive measure** | Whether a measure may legally be summed. `order_total` and `qty` add across any dimension (additive); a stock level or headcount adds across stores but not across days (semi-additive); ratios and averages like `avg_order_value` never add — store the parts and recompute. Storing a non-additive measure without its parts is how dashboards start lying. | A15, guides/data_modeling.md |
| **natural key** | An identifier that arrives with the data — `order_id` as shopcore assigns it. Free and meaningful, and *outside your control*: A10 is where the producer changes its type underneath you. | A03, A10 |
| **surrogate key / canonical key** | A key the warehouse controls, so a producer's change cannot break your joins. A10's canonical `order_id` + `order_id_num` is the cheap form — the source's meaning kept, the format owned by you; a true surrogate (sequence or hash of the natural key, natural key demoted to an attribute) decouples completely, at the cost of a key lookup on every load and one more hop when debugging against the source. | A10 |
| **denormalization** | Deliberately copying dimension attributes into a fact so readers need no join — `core.orders_enriched` carries `customer_country` and `store_region`. Buys query convenience with storage and a rebuild every time a dimension changes: a decision with a stated reason, never a default. | A03 |
| **SCD (Type 1/2/3)** | Slowly changing dimension — what happens when a customer's country changes. Type 1 overwrites and loses history (what `core.customers` does today, rebuilt from the dim file each run); Type 2 adds a row with `valid_from`/`valid_to`/`is_current`; Type 3 keeps a previous-value column. Type 2 is the one worth building, and the append log makes it a query rather than a pipeline. | A08, A15 (stretch) |
| **medallion (bronze/silver/gold)** | The layering vocabulary you meet in Databricks-flavored shops: raw landed → cleaned and conformed → consumption-shaped. This lab's `staging` / `core` / `marts` is the same ladder under different names — recognize the words, don't rename your schemas. | guides/data_modeling.md |
| **Kimball / Inmon / Data Vault** | The three warehouse design schools: dimensional marts built bottom-up per business process (Kimball), a normalized enterprise warehouse feeding downstream marts (Inmon), and hub/link/satellite structures built for auditable, insert-only loading (Data Vault). This lab is *Kimball-shaped* — one star, not a conformed-dimension bus — and never practises Inmon or Data Vault; the names are here so they aren't foreign in an interview. | guides/data_modeling.md (named only) |
| **era (v1/v2/v3)** | A period during which the source feed's schema was stable. Boundaries are where schema evolution happened. | A10 |
| **partition** | A subdirectory of the lake holding one value of the partition key (`order_date=2026-06-19/`), so queries can skip everything else. | A02 |
| **partition pruning** | The engine reading only the partitions a filter allows. The reason the lake is partitioned at all. | A02 |
| **row group** | The unit a Parquet file is internally chunked into; each carries min/max stats per column. | A01, A14 |
| **zone map** | Those min/max stats, used to skip whole row groups without reading them. Sorting your data makes them sharp. | A14 |
| **hive layout** | The `key=value/` directory naming convention for partitioned files. | A02 |
| **idempotent** | Safe to run any number of times with the same end state. The property that makes retries and backfills boring. | A07 |
| **upsert / MERGE** | Update-if-exists, insert-if-new, keyed on a unique id; latest version wins. | A08 |
| **delete+insert by date** | Refresh strategy: delete the affected date range, re-insert it whole. Idempotent by construction. | A07, A08 |
| **late-arriving data** | Rows for day T delivered in a later day's file. Why loading file D touches partitions D−7…D. | A02, A08 |
| **backfill / restatement** | Rebuilding history through the normal pipeline / changing already-published numbers (which people saw). | A11 |
| **atomic swap** | Publishing a rebuilt table/partition in one indivisible step so readers never see it half-done. | A09 |
| **torn read** | What a reader sees mid-rewrite without a swap: partial, duplicated, or missing data. | A09 |
| **data contract** | The versioned, agreed promise between producer and consumer — semantics, tolerances, SLAs, change policy. | A06 |
| **violation vs gap** | Data breaking a written contract rule (incident to report) vs surprising you where the contract is silent (amendment to propose). | A05, A06 |
| **hashing (PII)** | One-way transform (A06's `md5(lower(trim(email)))`): same input, same output, no way back. Equality survives — joins, dedupe, `count(DISTINCT …)` still work. A small value space can be brute-forced, so production PII gets a keyed hash (HMAC); plain `md5` is for the lab's synthetic emails. | A06 |
| **masking** | Destroying a value's content while keeping its shape (`l***@e***.com`) for human eyes — support screens, demos, log lines. Masked values no longer compare equal, so joins and dedupe die: a display-layer tool, never a storage-layer one. | A06 |
| **tokenization** | Swapping a value for a random token; only a separate, locked-down vault can reverse it, under access control and audit. Reversible on purpose — for the few consumers who need the original back (billing must actually email the customer) — and the heaviest to run: a vault is infrastructure. | A06 |
| **lineage columns** | Warehouse-added `_data_date` and `_run_id` — which business date the row was delivered for, and which run wrote it. Exactly two on purpose: the source file and the load time are facts about the *run*, so they live on the `ops.etl_runs` row `_run_id` points at instead of being copied onto 1.2M rows. | A03, A07 |
| **data lineage (row / table / column level)** | Where data came from, at three zoom levels: which delivery and run produced *this row* (`_data_date` + `_run_id` → the ledger), which tables feed *this table* (the dbt DAG), and which upstream column feeds *this column*. Unqualified, "lineage" usually means the table level; column lineage is what commercial catalogs automate and dbt does not show natively. | A03, A07, A15 |
| **freshness / staleness** | Whether the newest `_data_date` is as recent as the SLA promises. First thing to check when "the dashboard looks wrong". | A05, A11 |
| **quarantine** | Where rows that fail validation go — kept with a reason, never deleted, never silently fixed. | A05 |
| **reconciliation** | Proving loaded counts match the producer's manifest. The difference between "it ran" and "it's complete". | A05 |
| **pandera** | Declarative validation for DataFrames — your own A05 checks expressed as a schema object, with typed failure cases instead of hand-built SQL. Reads beautifully, but needs the rows in memory, which is why the lab's pipeline keeps the checks in SQL at 82M rows. | A05 |
| **Great Expectations** | The heavyweight of data quality: expectation suites, a results store, and generated data docs. Named, not installed — it brings its own config and backend, and `ops.dq_report` is the same idea at a size you can still read. | A05 (named only) |
| **pydantic** | Python's typed-model parser: describe a document as classes and it validates at load time, with `extra='forbid'` catching a typo'd key instead of silently disabling the rule. Right for the contract YAML (one small document, parsed once), wrong for the feed (82M rows = 82M Python objects). | A06 |
| **RSS** | Resident set size — a process's actual RAM footprint. What Task Manager shows and psutil samples. | A13 |
| **spill** | The engine writing intermediate data to disk when it hits its memory limit. Slower, but alive beats OOM. | A13 |
| **OOM** | Out of memory — the crash you get with no memory limit and no spill path. | A01, A13 |
| **oversubscription** | More busy threads than cores (e.g. 8 workers × 8 threads on 8 cores) — everyone context-switches, nobody finishes. | A12 |
| **skew / straggler** | Unevenly sized work units (spike days), and the one slow task everyone else waits for. | A12 |
| **predicate / projection pushdown** | The engine applying your filter / column list at the file scan, so unneeded data is never read. | A14 |
| **incremental model** | A dbt model that processes only the new window per run instead of rebuilding history — dbt's formalization of your A07/A08 pattern. | A15 |
| **data governance** | The rules around the data rather than in it: who owns a feed, what it promises, how it may change, how it's classified, what quality it must hold, and who ran what. Not a product you install — the lab builds nearly all of it (contract, tolerances, naming rules, run ledger, postmortems) before ever using the word. | guides/data_governance.md |
| **metadata (technical / operational / business)** | Data about the data: types, schemas and partitions (technical); run times, row counts, freshness and test results (operational); descriptions, ownership and meaning (business). The pipeline emits the first two for free; the third exists only if a human writes it, which is why a placeholder `description:` is worse than none. | A15, guides/data_governance.md |
| **data catalog** | A searchable inventory of tables and columns with their types, descriptions, tests, freshness and the DAG that connects them. `dbt docs generate` is one — say it out loud; DataHub, OpenMetadata, Unity Catalog and Glue are the commercial versions of the same idea. | A15 |
| **impact analysis** | Answering "what breaks if this changes?" *before* agreeing to the change — the producer proposes dropping a column, you walk the lineage graph (`dbt ls --select source:shopcore.orders+`) and reply with the affected models by name. The reason table-level lineage is worth having. | A15 |
