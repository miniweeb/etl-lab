## 3. The dataset

Synthetic e-commerce order feed. Generated by `datagen/generate.py`
(deterministic per date — same date always regenerates byte-identical).

### 3.1 Volume (why the lab hurts on purpose)

| Scale  | Baseline rows/day | Typical CSV/day | Total (69 days + dims) |
|--------|-------------------|-----------------|------------------------|
| full   | 1,200,000 (weekdays) | ~350 MB      | **~82M order rows, ~24 GB CSV** |
| small  | 60,000            | ~18 MB          | ~4M rows, ~1.2 GB      |

- Weekends: ×0.75. Deterministic per-date jitter ±5%.
- **Spike days** (flash sale): `2026-06-19` and `2026-07-11` at **×3** (~3.6M rows,
  ~1 GB CSV each). These create skew for the performance/resource assignments.
- Consequences on the 16 GB baseline (verified intent, referenced by assignments):
  - Loading all raw CSVs with pandas needs way more RAM than the machine has → dies.
  - One full-scale day in pandas ≈ 2–4 GB RSS → survivable but scary; DuckDB streams it.
  - Full-history unnest of `items` ≈ ~200M+ item rows → forces per-partition processing
    and memory-limit awareness.
  - 69 sequential per-day runs are slow enough (tens of minutes) that parallelization
    is genuinely worth it — and naive 8-way parallelism × default DuckDB memory blows
    the RAM budget, forcing real capacity math.

### 3.2 Dates and schema eras

| Era | Dates (inclusive) | Files | Notes |
|-----|-------------------|-------|-------|
| v1  | 2026-06-01 → 2026-07-15 | 45 | "Month 1". Stable schema. All of A01–A09 use only this. |
| v2  | 2026-07-16 → 2026-07-31 | 16 | Adds 3 columns at the end. |
| v3  | 2026-08-01 → 2026-08-08 | 8  | Type change + column rename + nested change. |

Month 2 (v2+v3) is generated **only when the student runs the generator with
`--month 2`** — assignment A10 stages this as "the upstream team shipped a new
export version". A01–A09 must not mention v2/v3 columns except as foreshadowing.

**Corrupt file:** `orders_2026-07-22.csv` contains ~3,000 structurally broken lines
(wrong column count) **and exactly one row with an unclosed quote**. Strict
`read_csv` fails on it; `store_rejects=true` handles it. Surfaces during A11 backfill.

### 3.3 Orders schema

CSV, header row, UTF-8, `,` delimiter, minimal quoting (JSON columns are quoted).

**Era v1 columns (exact order):**

| # | column | content | dirt (see 3.5) |
|---|--------|---------|----------------|
| 1 | `order_id` | BIGINT. `date_ordinal*10_000_000 + seq` where `date_ordinal = days since 2026-01-01`. Unique per order… almost (see dup dirt). | in-file dups 0.05% |
| 2 | `customer_id` | BIGINT 1..1,200,000 (small: 1..60,000), zipf-skewed | 0.15% empty; 0.05% orphan (id beyond dim); **0.2% Excel-float form `"123456.0"`** |
| 3 | `store_id` | INT 1..400 (both scales) | — |
| 4 | `order_ts` | `YYYY-MM-DD HH:MM:SS` (event time, within the file's date except late rows) | 0.4% `DD/MM/YYYY HH:MM:SS`; **0.3% ISO-T `YYYY-MM-DDTHH:MM:SS`; 0.02% impossible (e.g. `2026-06-31 12:00:00`) → must become NULL/quarantine** |
| 5 | `updated_at` | `YYYY-MM-DD HH:MM:SS`, always clean, ≥ order_ts | — |
| 6 | `status` | created/paid/shipped/delivered/cancelled/refunded (≈5/25/20/40/6/4%) | 0.3% junk: `"PAID "`, `"Paid"`, `"unknown"`, `""` |
| 7 | `payment_method` | card/wallet/bank_transfer/cod/paypal | 0.3% casing variants `"Card"`, `"CARD"`, `" cod "` |
| 8 | `order_total` | decimal string, = sum(items qty×price) | 0.2% `"N/A"`/empty; 0.1% negative; 0.5% mismatch vs items sum; **0.3% European decimal comma `"93,32"` / `"1.234,56"`; 0.2% currency prefix `"$79.98"`** |
| 9 | `items` | JSON array: `[{"sku":"SKU-000123","qty":2,"unit_price":19.99}, …]` 1–6 items (avg ≈2.6) | 0.2% of item SKUs orphans; **0.3% of rows have `qty` and/or `unit_price` as JSON *strings* (`"qty":"2"`) — JSON-level type normalization** |
| 10 | `meta` | JSON object: `{"device":"ios|android|web|desktop","utm":"google|facebook|tiktok|email|none","sess":"<hex8>"}` | utm is sometimes JSON `null`, sometimes the string `"none"`, sometimes the key is **absent** — three flavors of "no value" to normalize |

**Era v2** = v1 + three columns appended:

| column | content |
|--------|---------|
| `currency` | USD 94%, EUR 3%, GBP 2%, **VND 1%** — VND rows have amounts ×25,000 (item prices too, so totals still reconcile). Deliberate outlier bomb for averages. |
| `discount_amount` | 0 for 80% of rows, else up to 30% of items total. **In v2+, `order_total = items_total − discount_amount`** — the reconciliation rule changes with the schema version (data-contract lesson). |
| `channel` | web/app/marketplace/phone |

**Era v3** = v2 with three breaking changes:

1. `order_id` becomes **VARCHAR**: `ORD-0000000000` (`"ORD-" + zero-padded 10-digit`
   same numeric scheme — canonicalization must strip the prefix to match history).
2. `payment_method` is **renamed** to `payment_type`.
3. `items` structs gain a field: `{"sku":…,"qty":…,"unit_price":…,"disc":0.0–0.3}`;
   new top-level column `loyalty_tier` (70% empty, else bronze/silver/gold/platinum).

### 3.4 Late-arriving corrections (drives A08 delete+insert by date)

- Each day-D file (D > 2026-06-01) contains **~1.5% "late" rows**: orders whose
  `order_ts` falls on a prior day T ∈ [max(start, D−7), D−1], with an `order_id`
  drawn from T's real id range, `updated_at` on day D, status advanced
  (delivered/cancelled/refunded) and sometimes a changed total.
- Meaning: the same `order_id` appears in multiple files; latest `updated_at` wins.
- Meaning: **loading file D touches partitions D−7…D**, not just D.
- Era rule: late rows are formatted in the **file's** era (a v3 file carries
  corrections to v1-era orders as `ORD-…` strings — A10 exercise).

### 3.5 Dirt rates (single source: `datagen/profiles.py`)

late 1.5% · in-file dup order_id 0.05% (second copy has later `updated_at` and
advanced status) · dirty ts formats 0.4%+0.3% (+0.02% impossible) · junk status 0.3%
· payment casing 0.3% · order_total: "N/A"/empty 0.2%, negative 0.1%, European
decimal-comma 0.3%, "$"-prefix 0.2%, ≠items-sum 0.5% · customer_id: empty 0.15%, orphan 0.05%,
float-form 0.2% · orphan SKU 0.2% of items · string-typed numbers inside items JSON
0.3% of rows. Values dirty; **structure always parseable** except the one corrupt
file (3.2).

**Design intent:** the feed is ~97% clean (realistic), but *every* classic cleansing
and type-normalization pathology is present at teachable volume (0.2% of a 1.2M-row
day ≈ 2,400 rows — impossible to hand-fix, must be handled in code). A03 owns the
cleansing/normalization curriculum; A05 owns detecting what can't be fixed.

### 3.6 Dimensions

- `customers.csv`: `customer_id, name, email, country, city, signup_ts, is_active`.
  1.2M rows (small: 60k). Deliberately the dirtiest table per-capita — the dim-cleaning
  playground for A03:
  - `signup_ts`: ~80% `YYYY-MM-DD HH:MM:SS`, ~10% `DD/MM/YYYY`, **~8% epoch seconds**
    (e.g. `1712345678`), ~2% empty — one column, three types.
  - `is_active`: mixed booleans — `true/True/TRUE/1/yes/Y/false/0/no/N/` (empty).
  - `country`: variants of the same country — `US/USA/United States/us`,
    `VN/Vietnam/Viet Nam`, `GB/UK/United Kingdom` (+1% empty) → conformance mapping.
  - `name`: stray whitespace, SHOUTING CASE ~2%, `"LASTNAME, Firstname"` form ~3%.
  - `email`: 0.3% duplicated across customer_ids; 0.5% obviously invalid (no `@`).
- `products.csv`: `sku, product_name, category, subcategory, unit_price, tags, attrs`.
  40k rows (small: 2k). `tags` pipe-separated (`"wireless|audio|sale"`), `attrs` JSON
  (`{"brand":…,"weight_g":…,"color":…}`) — more complex-type practice. Dirt:
  0.5% `unit_price` in European decimal-comma form (`"29,99"`).
- `stores.csv`: `store_id, store_name, region, country, opened_date`. 400 rows.

### 3.7 Manifest files (drives reconciliation checks in A05)

`raw/manifest/orders_YYYY-MM-DD.json`:

```json
{"file": "orders_2026-06-01.csv", "date": "2026-06-01", "era": "v1", "scale": "full",
 "rows": 1234567, "late_rows": 18519, "dup_rows": 617, "corrupt_rows": 0,
 "bytes": 367001234, "min_order_ts": "...", "max_order_ts": "...", "generator_version": "1.0"}
```

`rows` counts data rows written **including** dup/late rows, excluding header and
corrupt lines. Reconciliation: loaded row count must equal manifest `rows`
(then dedupe explains the delta between raw and core).

### 3.8 Generator CLI

```
python datagen/generate.py --scale {small,full} [--month {1,2,all}]
       [--start YYYY-MM-DD --end YYYY-MM-DD] [--workers N] [--force] [--no-dims]
```

- `--scale` is required (prevents "oops I generated 24 GB").
- Skips files that already exist unless `--force` (generator itself demonstrates
  idempotent design — called out in A00/A07).
- Deterministic per date: seed = md5(date). Regenerating any file is safe.
- `datagen/selftest.py --scale small|full` validates counts vs manifests, era
  schemas, late-row id validity, dirt rates, corrupt-file behavior. A00 runs it.

### 3.9 Source system & the data contract

The producing application has a name: **shopcore**, the e-commerce OLTP
platform (Checkout Platform team). The feed is governed by a real, signed
contract checked into the repo:

- `contracts/shopcore_orders_daily.contract.yaml` — the agreed v1.3.0 contract:
  ownership/escalation, change management, delivery & freshness SLA,
  business-date semantics, per-column semantics (money: currency/scale/
  rounding/sign; timestamps: timezone/UTC-already-converted/warehouse keeps
  raw and converts only in marts), nullability/uniqueness/references, quality
  tolerances, latest-wins dedupe policy, and business rules (status
  transitions, refund sign convention, total==Σitems±0.01).
- `contracts/README.md` — anatomy of a contract + the per-column question
  checklist (what a DE must ask for money/timestamp/key/enum/JSON columns).

**Violation vs gap (mentor answer key — A05/A06 build on this):**
The contract makes some dirt a *violation* (stated rule broken → quarantine +
report to producer) and leaves other dirt a *gap* (contract silent → cannot
blame producer; propose an amendment):

| Dirt (§3.5) | Classification |
|---|---|
| negative order_total | **violation** (`negative_allowed: false`) |
| "N/A"/empty total, junk/padded status, payment casing | violation (types/enums/case pinned) |
| DD/MM + ISO-T timestamp formats, impossible dates | violation (written format pinned) |
| Excel-float customer_id `"123.0"` | violation (BIGINT promised) |
| total≠items sum > 0.01 | violation (business rule) |
| orphan customer/SKU beyond tolerance | violation (references + tolerances) |
| within-file exact re-sends ≤ 0.2% | **tolerated by contract** (at-least-once) |
| corrupt 2026-07-22 file | violation, *structural* → incident, not cleanup |
| European decimal-comma / `$`-prefix totals | **gap** (money clause silent on locale/symbols) |
| string-typed `"qty":"2"` in items JSON | gap (inner JSON types not pinned) |
| utm null vs `"none"` vs absent key | gap (null-representation unstated) |
| `updated_at` timezone/meaning | gap (deliberate silence, flagged by comment) |
| restatement/re-publish of old files | gap (no clause; treat as incident) |
| PII/retention (emails in customers feed) | gap (no data-classification clause) |
| max items array length | gap |

A06's core exercise is the **gap hunt**: students must find ≥4 of these
silences themselves (the YAML's `# NOTE` comments seed two).

## 4. Canonical DuckDB snippets (verified on duckdb ≥1.4)

Assignments must use these exact forms (adapted paths OK). Do not invent syntax.

```sql
-- Explicit-schema CSV read (era v1)
SELECT * FROM read_csv('<root>/raw/orders/orders_2026-06-02.csv',
    header=true,
    columns={'order_id':'BIGINT','customer_id':'BIGINT','store_id':'INTEGER',
             'order_ts':'VARCHAR','updated_at':'TIMESTAMP','status':'VARCHAR',
             'payment_method':'VARCHAR','order_total':'VARCHAR',
             'items':'VARCHAR','meta':'VARCHAR'});
-- order_ts/order_total read as VARCHAR on purpose: dirty values, cleaned in staging.

-- Dual-format timestamp cleanup
try_strptime(order_ts, ['%Y-%m-%d %H:%M:%S', '%d/%m/%Y %H:%M:%S'])

-- Amount cleanup ('$79.98', 'N/A', European '93,32'/'1.234,56', negatives)
TRY_CAST(NULLIF(
  CASE WHEN order_total LIKE '%,%'
       THEN replace(replace(order_total, '.', ''), ',', '.')
       ELSE replace(TRIM(order_total), '$', '') END,
  'N/A') AS DECIMAL(14,2))

-- Rejects handling (the corrupt file). Two nuances, verified on duckdb 1.5:
--   1. reject tables only fill on a MATERIALIZING scan — a bare count(*) is
--      optimized past parsing and leaves them empty. CREATE TABLE ... AS works.
--   2. a truncated line yields one reject row PER missing column — count
--      distinct `line` to count bad lines.
CREATE TABLE day_raw AS SELECT * FROM
  read_csv('...orders_2026-07-22.csv', header=true, store_rejects=true, ...);
SELECT count(DISTINCT line) FROM reject_errors;   -- bad source lines
SELECT error_type, count(*) FROM reject_errors GROUP BY 1;  -- and see reject_scans

-- Hive-partitioned write
COPY (SELECT *, CAST(order_ts_clean AS DATE) AS order_date FROM stg)
TO '<root>/lake/orders' (FORMAT parquet, PARTITION_BY (order_date),
                         APPEND, ROW_GROUP_SIZE 122880);
-- VERIFIED TRAP: in a per-day loop, OVERWRITE_OR_IGNORE silently CLOBBERS a
-- partition that an earlier day already wrote into (late rows share partitions!)
-- — day 2's 885 late rows replace day 1's full file. Use APPEND for incremental
-- loops (unique filenames per write; also see FILENAME_PATTERN). A02 stages
-- this failure deliberately; full-partition rewrites belong to A09's swap.

-- Hive-partitioned read (partition pruning)
SELECT count(*) FROM read_parquet('<root>/lake/orders/*/*.parquet', hive_partitioning=true)
WHERE order_date = DATE '2026-06-19';

-- Schema drift across files
SELECT * FROM read_csv('<root>/raw/orders/orders_*.csv', union_by_name=true, ...);

-- items JSON -> LIST<STRUCT> and unnest
SELECT order_id, unnest(
  CAST(items AS JSON)::STRUCT(sku VARCHAR, qty INTEGER, unit_price DOUBLE)[]
  , recursive := true) 
FROM stg;   -- alt: json_transform(items, '[{"sku":"VARCHAR","qty":"INTEGER","unit_price":"DOUBLE"}]')

-- meta JSON field
CAST(meta AS JSON)->>'device'    -- or json_extract_string(meta,'$.device')
-- note: ->>'utm' returns SQL NULL for BOTH JSON null and absent key; the string
-- 'none' stays a string — normalizing all three is an A04 task.

-- unnest cannot share a SELECT with GROUP BY — put it in a subquery:
SELECT tag, count(*) FROM (
  SELECT unnest(string_split(tags, '|')) AS tag FROM read_csv('.../products.csv', ...)
) GROUP BY 1 ORDER BY 2 DESC;

-- Upsert (duckdb >= 1.4)
MERGE INTO core.orders t USING stg_day s ON t.order_id = s.order_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

-- Delete+insert by date, atomically
BEGIN TRANSACTION;
DELETE FROM core.orders WHERE order_date BETWEEN ? AND ?;
INSERT INTO core.orders SELECT ... ;
COMMIT;

-- Profiling
EXPLAIN ANALYZE SELECT ...;
PRAGMA enable_profiling='json'; PRAGMA profiling_output='<path>.json';

-- Resource knobs
SET memory_limit='8GB'; SET threads=8; SET preserve_insertion_order=false;
SET temp_directory='<root>/tmp';
```

Python connection convention:

```python
import duckdb
con = duckdb.connect(str(WAREHOUSE))          # or duckdb.connect() for scratch
con.execute("SET memory_limit='8GB'; SET threads=8;")
```

### Per-assignment briefs (writers expand; scope is binding)

**A00 — Setup.** Python venv, `pip install -r requirements.txt`, set `ETL_LAB_DATA`
(warn: not OneDrive/Documents; need ~80 GB free; note per §7.4 temp discipline that
this volume also hosts all temp/spill — the OS drive never does), generate
`--scale small --month 1`, then `--scale full --month 1` (~10–20 min), run
`selftest.py`, tour the layout, open one CSV head in a pager (NOT Excel), rules of
the lab (dev on small, measure everything, keep a lab journal). **Git bootstrap**
per §7.4: `git init` + `main`, walk the shipped `.gitignore` (what's excluded and
why), `git config user.name/email` + `core.editor "notepad"`, first commit; explain
the commit-message editor screen before anyone meets it cold; state the
per-assignment branch→commit-per-task→merge-on-DoD ritual with a pointer to
`guides/git_basics.md`. **Month 2 is not generated yet** — A10 does that.

**A01 — First contact.** Feel the data before moving it. Tasks: list files + sizes
(PowerShell), count rows of one file with DuckDB (`SELECT count(*) FROM read_csv(...)`)
vs the manifest; `DESCRIBE`, `SUMMARIZE` one day (small first, then full);
**the pandas trap**: `pd.read_csv` one full day while watching Task Manager / psutil
RSS (~GBs), then *estimate* (don't run) 69 days; contrast DuckDB streaming count RSS.
Explicit-schema read (§4) vs auto-detect — find what auto-detect gets wrong
(order_id on v3 later; dirty ts). Load one clean day → single Parquet file; compare
CSV vs Parquet size (~5×) and count/filter/aggregate timing. Peek at row groups via
`parquet_metadata()`. DoD: student states rows/bytes for a chosen day matching
manifest, and can articulate why columnar+typed beats text.
**Mentor lens:** the 69-day pandas RAM figure is extrapolated from one measured day (never run), and the student names something concrete auto-detect got wrong — not just "Parquet is smaller".

**A02 — Partition the lake.** Concept: directory-as-index (Hive layout). Tasks:
per-day loader (function `load_day(date)`) reading raw CSV with explicit schema,
minimal casts, derive `order_date = CAST(cleaned order_ts AS DATE)`, `COPY …
PARTITION_BY (order_date)` (§4) into `lake/orders/`. Loop over month-1 dates
sequentially, timing each day (this slow loop is deliberately naive — A12 fixes it).
Observe: partition folders ≠ 45 — late rows create/write into earlier `order_date=`
partitions (discovery moment; foreshadow A08). Prove pruning: same aggregate over
one day via partition filter vs full-scan without, timings + `EXPLAIN`. DoD: lake
exists for month 1, pruning demonstrated, wall-clock recorded in journal.
**Mentor lens:** explains unprompted why partition folders ≠ 45 (late rows writing earlier `order_date=` dirs), and pruning is shown in `EXPLAIN`, not just a faster stopwatch.

**A03 — Transformation, cleansing & type normalization.** Layered model: raw →
staging (clean, typed, 1:1) → core (joined, enriched). This is the *data cleansing
curriculum* — the student builds a cleaning catalog, one rule per pathology (§3.5),
and every rule must be **counted** (how many rows did it touch?), never silent.
Also introduces two lab-wide standards (§7.1/§7.2) with a short concept box each:
**shared-warehouse naming** (source-prefixed staging tables — `staging.
shopcore_orders_day` etc., why bare `users` is unacceptable, why core may use
conformed short names) and **lineage columns — exactly two** (§7.2:
`_data_date` + `_run_id`; `_run_id` stays NULL until A07 gives it meaning;
`max(_data_date)` as the instant staleness probe). The box must teach the
*restraint*, not just the columns: a junior's instinct is to also stamp
`_source_file` and `_loaded_at` on every row, and those are facts about the
**run**, not the order — they live on the `ops.etl_runs` ledger row that
`_run_id` points at (A07 demos the join). In this feed the file name is
derivable from `_data_date` anyway (one file per business date, per the
contract's `path_pattern`). Stretch: write one day both ways and compare Parquet
size — the difference is tiny because dictionary encoding crushes 69 distinct
strings, which is the point: the reason is *modeling*, not bytes.
Tasks in `warehouse.duckdb`: staging table for one day using §4 cleaners —
timestamps: 3 formats via `try_strptime` list + impossible dates → NULL;
`order_total`: strip `$`, convert European decimal-comma form (`replace()`), NULLIF
'N/A', TRY_CAST to DECIMAL; `customer_id`: Excel-float `"123.0"` → BIGINT (cast via DOUBLE);
status/payment: TRIM + LOWER + map junk → NULL (CASE or a seed mapping table);
exact-duplicate removal only (full dedupe logic is A08's). Dim cleaning:
`core.customers` with `signup_ts` (string formats **and** epoch seconds via
`to_timestamp`), `is_active` mixed booleans → BOOLEAN, `country` → ISO-2 conformance
mapping table, names TRIM/casing/`"Last, First"` split; products `unit_price`
de-comma'd. **Modeling frame** (§7.7 — A03 owns the introduction, since this is where core
tables are first designed; A15 only recaps): a short box before the core build —
every table states its **grain** in one sentence ("one row = one order"), and
`core.orders_enriched` is a **fact** (events + measures) while `core.customers` /
`core.products` / `core.stores` are **dimensions** (entities + attributes you
filter and group by). Then `core.orders_enriched` = staging ⋈ customers ⋈ stores
with derived cols (order_hour, is_weekend, total_bucket) — and the doc names this

**A09 — Atomic partition swap.** Why: a reader querying the lake mid-rewrite sees

## 7. Conventions & guardrails

### 7.1 Naming (the warehouse is a shared namespace)

A warehouse hosts data from many applications; names must say *whose* data and
*which* definition. Lab-wide rules (introduced in A03, enforced everywhere):

- **staging** = landing zone, one table per source feed, **source-prefixed**:
  `staging.shopcore_orders`, `staging.shopcore_orders_day` (day-scoped working
  table). A customers feed staged the same way would be
  `staging.shopcore_customers` (this lab cleans customers straight into
  `core.customers`, so no such table exists). A second app's users table would
  land as `staging.adsight_users` — bare `users` is never acceptable in a
  shared schema.
- **core** = conformed business entities owned by the DW team, one agreed
  definition each: `core.orders`, `core.customers`. Short names are earned
  here *because* the layer conforms sources; still never generic/ambiguous
  names (`users`, `data`, `log`, `final`, `tmp2`).
- **marts** = purpose-named consumption tables (`marts.daily_store_sales`).
  **ops** = pipeline metadata only (`ops.etl_runs`, `ops.dq_report`, `ops.alerts`).
- snake_case; plural entity names; no SQL reserved words; metadata columns
  underscore-prefixed. dbt (A15): source `shopcore`, staging models
  `stg_shopcore__orders` (double-underscore convention).
- Lake dirs: this lab has a single source so `lake/orders…` stays short; the
  A03 naming box notes a multi-source lake would use `lake/shopcore/orders/`.

### 7.2 Lineage columns — exactly two (added at staging, carried into core)

Every staging and core row carries **two** warehouse-added columns, and no more
(the source never ships these — ingest adds them):

| column | type | meaning |
|---|---|---|
| `_data_date` | DATE | business date of the delivery this row came from (the *sync date*). Load-bearing: it is the DELETE/refresh key for idempotent reloads (§4), the partition key, and the staleness probe — `max(_data_date)` answers "how fresh is this table?" in one query. |
| `_run_id` | BIGINT | foreign key into `ops.etl_runs` (§7.3): "which run wrote this row?" NULL until A07 creates the ledger. |

**Everything else about the load lives in the ledger, not on the row.** Join
`core.orders o JOIN ops.etl_runs r ON r.run_id = o._run_id` to recover the
source file, the load timestamp, the status, the row count, and the error — one
ledger row per attempt instead of the same string copied onto 1.2M rows.

Why this is the standard (taught explicitly in A03; a junior's instinct is to
add more):

- **A fact about the load is not a fact about the order.** `source_file` and
  `loaded_at` describe the *run*; `order_ts` and `status` describe the *order*.
  Mixing them denormalizes log data into the fact table — and if you re-load a
  date from a corrected file you must rewrite 1.2M copies of a value that
  should have changed in exactly one ledger row.
- **In this feed the file name is derivable anyway**: the contract's
  `path_pattern` is one file per business date, so `_data_date` *is*
  `orders_<_data_date>.csv`. Storing both is storing the same fact twice.
  (Caveat worth stating to students: a feed with many files per date genuinely
  needs the file name — and it still belongs on the ledger row, keyed by run.)
- **Not primarily a storage argument.** A03's stretch has students measure it:
  in Parquet, a 22-char file name with only 69 distinct values dictionary-encodes
  down to almost nothing. The modeling reason is the real reason — which is
  exactly why the measurement is worth doing.

A05 uses `_data_date` for the freshness check; A07 gives `_run_id` meaning and
demonstrates the join that recovers the rest; quarantine rows additionally carry
`reject_reason` and `_rejected_at` (payload-specific, not lineage).

### 7.3 Audit, logging, alerting

- `ops.etl_runs` (A07): the run ledger — every attempt, status, rows, error.
  History is never deleted; A11 queries it as the audit trail. Canonical shape
  (A07 owns the DDL): `run_id BIGINT PRIMARY KEY, run_date DATE, step VARCHAR,
  status VARCHAR, started_at TIMESTAMP, finished_at TIMESTAMP, rows BIGINT,
  source_file VARCHAR, error VARCHAR`. **`source_file` lives here — not on data
  rows** (§7.2); `finished_at` is the load timestamp that a `_loaded_at` column
  would otherwise duplicate.
- Per-run log file `logs/run_<run_id>.log` via Python `logging` (console +
  file), introduced in A07.
- `ops.dq_report` (A05): one row per (date, check) with pass/fail + counts.
- `ops.alerts(alert_ts, run_id, severity, source, message)` (A05): written on
  DQ-threshold breach and freshness breach (A11: file missing/stale beyond
  contract SLA); console print + non-zero exit simulate paging. Severity:
  `warn` (tolerance edge) / `error` (hard fail).

### 7.4 Engineering practice (git · composability · preflight · temp discipline)

**Git ritual** (defined once here + `guides/git_basics.md`; A00 sets it up, every
doc's Setup carries the one-line reminder):
- A00: `git init`, default branch `main`, walk the shipped `.gitignore`, set
  `user.name`/`user.email`, and `git config core.editor "notepad"` on Windows —
  defusing the "commit message screen" before it ever traps anyone (the guide
  also teaches the vim rescue: `Esc :wq` / `Esc :q!`).
- Per assignment: branch `aNN-<topic>` (`git switch -c a03-transformation`) →
  commit after each numbered task (`A03 task 4: staging cleaners`; imperative,
  subject ≤ 72 chars) → merge to `main` when the DoD is green
  (`git switch main && git merge --no-ff a03-transformation`).
- Savepoints & rollback are taught where they hurt: A07 (chaos) demonstrates
  `git log --oneline`, `git checkout <sha> -- file`, `git restore`, and
  `git reset --hard` back to the last green commit.

**Composable code ladder.** Students grow a small package in `work/`, core →
feature; later assignments IMPORT earlier modules, never re-paste:
`lib/labpaths.py` (given) → `work/cleaners.py` (A03) → `work/validate_day.py`
(A05) → `work/contract_check.py` (A06) → `work/a07_load_day.py` +
`work/preflight.py` (A07) → `work/pipeline.py` (the A07 loader stitched into an
importable module) + `work/runner.py` (A11) → `work/parallel_runner.py` (A12).
Rules: every
module has a docstring stating its job and its assumptions; comments state
constraints, not narration; every module gets a pytest file in `tests/`
(pattern set by A03's `tests/test_cleaners.py`: run each cleaner over a VALUES
table in an in-memory DuckDB, assert expected outputs). `pytest` is in
requirements.txt; `python -m pytest tests/ -q` must be green before a branch
merges — that line joins the DoD ritual from A03 on.

**Preflight standard** (`work/preflight.py`, built in A07, called by every
runner from then on). Fail fast, before touching data, one PASS/FAIL line +
fix-hint per check:
1. data root exists and is **writable** (create+delete a probe file — reading
   a permission error at hour 0 beats one at row 40 million);
2. free space on the DATA volume ≥ threshold (not on C:!);
3. `temp_directory` resolves to the data volume (see temp discipline below);
4. source file for the date exists, size > 0, manifest present;
5. warehouse dir writable; DB file not locked by another process (the classic
   Windows "file in use" — second connection attempt catches it);
6. schemas exist / are creatable (`CREATE SCHEMA IF NOT EXISTS` doubles as a
   permission probe);
7. contract file present and parseable.
Teaching note carried with it: on a networked warehouse the same discipline
probes a different stack — DNS resolves? port reachable
(`Test-NetConnection host -Port 5432`)? TLS handshake? credentials valid?
`GRANT`s on schema/table? connection-pool headroom? — same checklist, layer
swapped. `guides/troubleshooting.md` holds both columns.

**Temp discipline.** Spill/temp ALWAYS lives on the working/output storage
(`<DATA_ROOT>/tmp`), never the OS drive. Rationale (taught in A00, enforced by
preflight #3, experienced in A13): provisioned machines typically pair a small
OS disk with large attached storage; an engine spilling tens of GB to the OS
drive fills it silently, and a full OS drive takes down everything else on the
box — a hidden failure point that surfaces only under load. DuckDB's *default*
temp location (beside the DB file / cwd) is only safe because our warehouse
already sits on the data volume — the convention block pins it explicitly
anyway, and A13 verifies where spill actually lands.

### 7.5 Industry tools: hand-roll first, then name the tool

The lab deliberately hand-rolls validation in SQL before naming any framework —
a junior who has written the checks understands what a tool is doing for them.
But a junior who has never *heard* of the standard tools interviews badly and
reinvents wheels on the job. So each hand-built thing gets a named successor:

| What the student built | Industry tool | Taught in | Installed? |
|---|---|---|---|
| Contract YAML read with `yaml.safe_load` + dict access | **pydantic** — parse the contract into a typed model; unknown keys and wrong types fail at load, not at 3 a.m. | A06 | yes (small, pure-python) |
| Per-column SQL check suite + thresholds | **pandera** — declarative DataFrame/schema validation with the same checks expressed as a schema object | A05 | yes (optional task; pip-installable, no services) |
| Quarantine + `ops.dq_report` + alerting | **Great Expectations / Soda** — suites, data docs, and a results store; heavier (own config + backend) | A05 (discussed, not installed) | no — by design |
| dbt generic + singular tests | **dbt-expectations** package (GE's assertions as dbt tests) | A15 (named) | no |

Two rules for these sections: (1) the tool never replaces the hand-built version
in the pipeline — it is shown side by side so the student sees the same rule in
both forms; (2) each gets a **"when NOT to use it"** line. The sharpest one is
pydantic: it is right for the contract (one small document, parsed once) and
wrong for 82M data rows (per-row Python objects) — that contrast is the lesson,
not a footnote.

### 7.6 Governance, catalog, metadata & lineage

The lab already *does* most of governance without ever using the word; the map
lives in `guides/data_governance.md`, which points at where each piece is built
rather than teaching it again:

| Governance concern | Where the lab does it |
|---|---|
| Ownership & escalation | contract `producer`/`consumer` blocks (A06) |
| Interface promises & change control | the contract + semver + notice policy (A06, A10) |
| Data classification / PII / retention | A06's classification clause + `email_hash` (A06, A15) |
| Quality standards & enforcement | contract tolerances → A05 checks, quarantine, `ops.dq_report` |
| Naming & shared-namespace rules | §7.1 (A03) |
| Audit trail (who/what/when ran) | `ops.etl_runs`, `ops.alerts`, `logs/run_<id>.log` (A07, A11) |
| Incident process | A11 postmortem + producer incident notes (A05, A06, A11) |
| Access control | **named, not practiced** — file-based lab; the networked-DB column of `guides/troubleshooting.md` covers GRANTs as a failure mode |

**Three levels of lineage** — the lab teaches all three, and the guide names them
so students don't think "lineage" means only the columns:

1. **Row-level provenance** — `_data_date` + `_run_id` → the ledger (§7.2, A03/A07).
   Answers "where did *this row* come from?"
2. **Table/model-level lineage** — the dbt DAG (A15). Answers "what feeds this
   table, and what breaks if the source changes?" A15 makes this concrete with an
   **impact-analysis task**: shopcore announces dropping a column; use
   `dbt ls --select source:shopcore.orders+` and the docs DAG to answer *what
   breaks* before agreeing to the change (ties back to A06's change_management).
3. **Column-level lineage** — named in A15 (dbt docs shows model-level; column
   lineage is what commercial catalogs add); the student traces one column by
   hand, `order_total` → `marts.daily_store_sales.gross_revenue`, to feel what a
   catalog automates.

**Catalog**: A15's `dbt docs generate` **is** a data catalog — the lab must say so
explicitly (searchable table/column descriptions, types, tests, the DAG,
freshness). `schema.yml` `description:` fields are the metadata being catalogued,
so A15 requires real descriptions on the models and key columns, not placeholders,
and names the commercial equivalents (DataHub, OpenMetadata, Unity Catalog,
Glue Data Catalog) in one line.

### 7.7 Data modeling (the shape of the target, not the plumbing)

The lab is strong on *moving* data and light on *designing* the target, so the
modeling thread is deliberate and threaded, not a separate assignment. Full
reference: `guides/data_modeling.md`. Three lab-wide rules:

**1. Every table states its grain.** One sentence — "one row = one …" — as a
comment on the DDL and as the dbt `description:` first line. A table whose grain
you cannot say in one sentence is a table you have not designed. Introduced in
A03 (first core tables), exercised in A04 (unnest *changes* grain: order grain →
item grain), enforced in A15's descriptions.

**2. Keys are a decision, not an inheritance.** Two kinds:
- **natural key** — comes from the source (`order_id` as shopcore assigns it).
  Free, meaningful, and *outside your control*.
- **surrogate / canonical key** — one the warehouse controls, stable across
  producer changes.

A10 is where this stops being theory: shopcore changes `order_id` from `BIGINT`
to `'ORD-0000000000'` mid-course. The canonical `order_id` (+ `order_id_num`)
the student already builds there **is** a warehouse-controlled key — the docs
must name it as such, and state the trade-off (a pure surrogate, e.g. a hash or
sequence, decouples you completely but costs a lookup on every load and makes
debugging against the source harder; the lab's canonicalization keeps the
source's meaning while owning the format). A10 owns this lesson.

**3. Facts and dimensions are chosen, not given.** A *fact* records events at a
stated grain and carries measures; a *dimension* describes the entities a fact
references and carries attributes you filter and group by. Introduced in **A03**
(where `core.orders_enriched` and `core.customers` are first built — not in A15,
which only recaps), and A03 also names the deliberate denormalization: joining dims
into `core.orders_enriched` trades storage and refresh cost for query
convenience, which is a *decision* with a stated reason, not a default.

**Fact types** (named in A15, since the lab builds two of the three):
transaction fact = one row per event (`fct_orders`, `fct_order_items`);
periodic-snapshot / aggregate fact = one row per entity per period
(`marts.daily_store_sales`); accumulating-snapshot fact = one row per process
instance with a column per milestone (the order lifecycle would be one — named,
not built).

**The design act.** Every student must, at least once, *decide* a model rather
than implement a given one. A15 owns this: a fresh business question, and the
student writes grain / keys / dimensions / measures / refresh strategy **before**
any SQL, then compares against a reference answer that argues the trade-offs
rather than declaring one right answer.

**Named, not practiced** (so the words aren't foreign in an interview):
Kimball (dimensional, bottom-up) vs Inmon (normalized enterprise warehouse,
top-down) vs Data Vault; snowflake schema; bridge tables for many-to-many; and
the **medallion** vocabulary — this lab's `staging` / `core` / `marts` is
bronze / silver / gold under different names, and the guide says so explicitly.
SCD Type 1/2/3 are named in the guide; Type 2 is built in A08's and A15's
stretch goals.

### 7.8 General guardrails

- Never `SELECT *` into pandas at full scale except where a trap is the lesson —
  and then with a stated abort guard.
- Every measured claim in docs is hedged ("on the baseline machine, expect
  roughly…") — exact numbers only when derived from manifests/determinism.
- Journal: students keep `journal.md` (per-assignment timings/observations);
  referenced by A01, A02, A11–A14.
- Databases: schemas `staging`, `core`, `marts`, `ops` inside `warehouse.duckdb`.
- All scripts students write live in `work/` in the repo (gitignored? no — their
  work is the point; `data/` is gitignored).
